Claude Code caches a conversation's prompt with a **1-hour TTL** (its requests carry
`cache_control: {ttl: "1h"}`). While a warmed session is idle, keep-warm replays its last request
every ~50 min — inside that 1-hour window, so it lands as a **cache-read** and resets the timer,
instead of letting the cache expire and forcing a full re-process on your next turn.

<KeepWarm />

:::note[What a ping actually costs]
A ping is a **cache-read**, which is far cheaper than fresh input:

- **On pay-per-token API billing:** cache reads are ~**0.1×** the normal input price (Anthropic's
  published rate).
- **On a Claude Code subscription (Pro/Max/Team):** there's **no per-token dollar cost** — you have
  rate-limit windows (5-hour + weekly). In our own measurements, **fresh input moved the 5-hour
  meter ~1% per a few-hundred-thousand tokens, while millions of cache-read tokens moved it ~0%** —
  i.e. a ping barely touches your rate limit. (Plan size sets the window: a bigger plan absorbs more
  before the meter ticks.)

Either way, a ping costs a small fraction of what a cold re-process of the whole context would.
:::

```bash
claudex keep-warm start                # start the proxy + wire ANTHROPIC_BASE_URL
claudex keep-warm add <session|--last> # warm a session
claudex keep-warm status               # (default) what's being warmed
claudex keep-warm rm <session>         # stop warming one
claudex keep-warm stop                 # restore settings.json
```

**Flags:** `target` (session id / id-prefix / project), `--last`, `--interval <MIN>` (default 50,
max 55 — under the 60-min TTL), `--max <HRS>` (stop after N idle hours, default 8), `--no-wire`.

**Note:** a session is only warmable *after* it routes through the proxy (the cacheable prefix lives
in the live request, not on disk) — nothing is grabbed retroactively. Each warmed session stays on
its own account. Mutually exclusive with **[pool](/pooling/overview/)**.
